MirchiLime Connect · reference document

Dotted and solid.

Every truck already had a position source — FASTag toll crossings, sparse but certain. This adds a second, independent one: the driver's own phone, tracked through Telenity's SmartTrail network API. Both are drawn on the same map, and neither is ever allowed to masquerade as the other — a solid line for what a toll crossing has confirmed, a dotted one for where the SIM says the truck has got to since. This is the reference for what actually shipped: schema, rendering logic, the Telenity integration, and every file that changed to build it.

How the pieces fit

SYSTEM OVERVIEW

The two position sources never touch each other. Each has its own external API, its own poller, its own table, and its own failure mode — the only place they meet is the map, which reads both and draws two lines. That separation is deliberate: a bug in the SIM pipeline can't corrupt a toll crossing, and vice versa.

A row only exists for a fix that actually landed

poll_sims() only inserts into sim_pings when Telenity's response has retrieved true and both coordinates present. A failed or not-yet-computed check updates truck_sims.last_error and stops there — no placeholder row, no null-coordinate row to filter out downstream. This also means there is no deduplication step: two identical successive positions both get their own row, which is fine for a trail but worth knowing if you ever count pings as a proxy for "checks made."

CREATE INDEX idx_sim_pings_vno_time ON sim_pings (vehicle_no, pinged_at) — every read is "this truck, ordered by time," so that's the only index it needs.

The map drawing logic

SOLID CONFIRMS, DOTTED LEADS

Both lines are drawn at a similar weight — 4 or 5 px, not "thick vs. thin." The differentiator that actually matters is the dash pattern and, more importantly, which one paints on top. The SIM trail is drawn first; the toll route is drawn second and raised with .bringToFront() — so wherever a crossing later confirms ground the SIM already reported, the solid line physically overwrites the dotted one. That is the whole visual grammar: dotted is a claim, solid is a receipt.

Implemented in three places, the same way each time

Live Routes and Journey Timeline live in hundred_trucks.html; the public link is track.html. All three build the SIM trail identically:

const simPts   = simPings.map(p => [p.lat, p.lng]);
// anchor at the last confirmed toll so the dotted line bridges from there —
// a single SIM ping otherwise draws nothing at all
const trailPts = last ? [[last.lat, last.lng], ...simPts] : simPts;
if (trailPts.length > 1) {
  L.polyline(trailPts, { color, weight: 4, opacity: 0.95, dashArray: '2,8', lineCap: 'round' })
    .addTo(map);
}
// ...toll route drawn after, and raised:
L.polyline(routePts, { color, weight: 5, opacity: 0.95 }).addTo(map).bringToFront();

Freshest wins

The truck's "current position" — the marker, the location text, the map's fit-bounds — is whichever signal is newer. Both the Live Routes overview and track.html compare the newest SIM ping's timestamp against the last crossing's and use whichever is later: 

const simFresher = !!(newestSim && newestSim.lat &&
                      (!last || simTs(newestSim.pinged_at) > simTs(last.crossed_at)));
const currentCoord = simFresher ? [newestSim.lat, newestSim.lng]
                   : last       ? [last.lat, last.lng] : null;

The truck marker

The old pulsing diamond became a side-view container truck, MirchiLime yellow tractor fixed on every truck, container coloured per-truck so it still matches its route line and legend chip. It rotates to face its direction of travel, computed from the last two position fixes (bearingDeg()), with two corrections that keep a flat side-view sprite looking right at any heading:

  1. Mirror, don't over-rotate, past due-west. A plain rotation of a sprite drawn facing right would turn the truck upside-down heading west; instead the SVG is mirrored horizontally (scaleX(-1)) and rotated by the supplementary angle, so the nose still tracks the heading and the wheels stay underneath.

  2. Cap the tilt at MAX_TILT = 65°. An uncapped rotation stands the truck on end at due north or south. 65° stays clear of vertical while still keeping all eight compass directions visually distinct — a 45° cap would make north and north-east render identically.

Applied identically on hundred_trucks.html (per-truck colour) and track.html (one fixed blue container, since a public link only ever shows one truck).

The Telenity integration

SMARTTRAIL — A PROVISIONING LIFECYCLE, NOT A LOOKUP

The first assumption going in — that tracking a driver would be one API call with a phone number in and coordinates out — was wrong, and finding that out shaped most of telenity.py. Telenity's model is a lifecycle: a driver has to opt in over SMS or IVR before any location call returns anything, and we, not Telenity, have to notice that consent landed and flip tracking on ourselves.

Resend is Jio-specific — Airtel, Vi and BSNL have no re-initiate endpoint at all, so their drivers only have the IVR line. Telenity lock a number at the operator level for 24 hours if the consent SMS is resent too often, so can_resend() refuses inside SIM_RESEND_COOLDOWN_HOURS, and the Driver SIMs screen's bulk "Resend all selected" quietly skips any row still in cooldown rather than firing at it.

Mock mode

MOCK_MODE = bool(SIM_MOCK) or not telenity.CONFIGURED — with the two TELENITY_*_BASIC variables unset, the whole feature still runs. Positions are generated by projecting forward from a truck's last two real toll crossings at ~38 km/h along their heading, seeded per hour so a trail builds smoothly across repeated calls, and the consent sweep approves instantly. Every mock row is tagged sim_pings.source = 'mock', so going live is DELETE FROM sim_pings WHERE source='mock' — no schema change, no data to reconcile by hand.

Licences

The pilot has 50 Telenity licences, one consumed per driver from Import until removed — release can take up to 24 hours to actually free the licence back up. telenity.licence() backs the count shown on the Driver SIMs screen and gates telenity_smoke.py's walkthrough from starting with zero left.

The only file that talks to Telenity's HTTP API. Nothing above it knows or cares about hosts, auth headers, or Telenity's response shapes.

An interactive CLI that walks one real driver through the entire lifecycle, colour-coded terminal output, one step at a time. Running in production

HOW THE SCHEDULER ACTUALLY WORKS, AND WHERE IT DOESN'T EXIST AT ALL

wsgi.py runs an in-process APScheduler BackgroundScheduler inside Gunicorn — no external cron. Because Gunicorn can run multiple workers, the scheduler setup is guarded by an fcntl.flock on /tmp/hundred_scheduler.lock, so only the first worker to grab the lock registers jobs; every other worker hits BlockingIOError and skips registration silently. ping_sims joins the existing FASTag and credit-trip jobs in that same locked block.

This startup block only catches one exception type

The scheduler setup runs at module import time, outside any if __name__ == '__main__': guard — and the surrounding try/except only catches BlockingIOError. Any other exception raised while registering jobs (for instance, a malformed cron string from SIM_PING_HOURS or SIM_PING_MINUTES) would crash the entire application at import, not just fail to schedule the SIM job. This is an existing characteristic of the file, not something introduced here — but the two new SIM env vars now feed directly into that same unguarded path, so a typo in either is worth double-checking before deploying.

server.py, the local dev mirror, has no scheduler at all — nothing runs on a timer locally. That is exactly why it gained manual trigger endpoints (/api/ping-sims, /api/sweep-consents, /api/sync-enroute, /api/ping-truck, /api/ping-all-connected) that production reaches only through cron: every "scheduled" production behaviour needs a manual equivalent to be testable locally at all.

Testing

AUTOMATED CHECKS, AND A SAFE WAY TO TEST AGAINST THE REAL API

test_backend.py — section 9

Self-cleaning, against the existing test truck. Assign a SIM, confirm has_sim flips true on the fleet list, ping once and confirm a fix lands in truck-detail and on the public track token, then remove it and confirm has_sim flips back.

telenity_smoke.py — one real driver, deliberately slow

Testing against Telenity directly has real costs — an SMS sent, a licence spent — so this script never does anything state-changing without a typed confirmation, always checks read-only state (licence count, consent status, entity search) before acting, and never retries blindly. That discipline came directly out of diagnosing the lastName bug: the read-only checks are what ruled out the wrong hypothesis before the real one-line cause was found. 

python3 telenity_smoke.py 919876543210 "Ramesh Kumar"   # full walkthrough
python3 telenity_smoke.py 919876543210 --status          # read-only check
python3 telenity_smoke.py 919876543210 --remove          # release the licence

Open items

FLAGGED, NOT BLOCKING

Jio resend, live

The resend flow is implemented and cooldown-gated but has not yet been fired against a real Jio number end-to-end — only Airtel/Vi numbers have been tested live so far.

DoT/TRAI consent

India's telecom rules require subscriber consent before a location lookup. truck_sims.consent_status exists and Telenity's own SMS gate enforces opt-in at their end, but nothing on our side independently enforces or audits it.

Accuracy, unverified

Telenity's fixes are network-based, not GPS. telenity_smoke.py prints a Maps link for a manual eyeball check, but no formal accuracy number has been established yet.

SIM_MANUAL_ENTRY

Numbers are entered by hand in the dashboard today. The flag exists specifically so this can flip to Zoho-sourced numbers (source='zoho' rows) later with a one-line change.

Static file exposure

Flask's static_folder serves files without going through DASHBOARD_KEY — a pre-existing gap, unrelated to this feature, flagged previously and still open.
