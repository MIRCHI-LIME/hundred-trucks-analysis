MirchiLime Connect · SmartTrail build plan

From mock
to live.

The Telenity documentation has arrived, and it describes a different shape of service than the one we built against. Driver tracking is not a lookup you call with a phone number — it is a provisioning lifecycle that only starts producing positions once the driver has replied to a text message.

Correcting what I told you earlier

I said going live would mean rewriting one function and setting two environment variables. That was based on my guess at the API's shape, and the guess was wrong. The maps, the database and the scheduler all stand; the client layer in sim_location.py needs restructuring. Roughly a day's work, not ten minutes.

What stands, what changes

Most of the build survives

Maps and tracking page

Unchanged. Dual lines, freshest-wins position, the truck marker and the customer link are all independent of how positions are fetched.

Database tables

Additive changes only. Both tables survive; they gain columns for the Telenity entity id, consent state and the address text the API returns.

Scheduler

Unchanged in shape, one job added for consent chasing.

Mock mode

Kept. It stays behind the same seam so the demo keeps working while credentials are pending, and so we can develop without burning licences.

Client layer

Rewritten. Two hosts, two authentication schemes, token caching, and six endpoints instead of one imagined call.

Accuracy radius

Removed. I invented it; the API returns no such field. It is replaced by detailedAddress, a readable place name, which is better and lets us stop geocoding coordinates ourselves.

The build

Seven phases · each one testable before the next

  1. Telenity client needs credentials

    A new telenity.py holding nothing but the API. Splitting it from sim_location.py keeps our own logic — schema, mock, polling — separate from their contract, so future API changes touch one file.

    It handles the part the documentation makes fiddly: two hosts with two different authentication schemes. The main API uses a Token header valid six hours; consent lives on a separate host behind an OAuth bearer valid one hour. Both get cached and refreshed automatically when a call returns 401.

    import_entity()    register a driver, fires the consent SMS
consent_status()   ALLOWED / PENDING / expired
set_tracking()     switch tracking on once consent lands
location()         one number
bulk_locations()   up to 200 numbers in a single call
delete_entity()    remove a driver, frees the licence
licence()          how many licences are left

    Their documented error codes get mapped to plain language once, here — phone switched off, out of coverage, not provisioned — so the rest of the system never handles raw numbers.

  2. Schema additions can start now

    All additive, so nothing existing breaks. Drivers gain a Telenity entity_id (needed to enable tracking), real consent state, and an expiry date. Positions gain the address text, the result status, and the speed and distance the bulk call returns.

  3. Onboarding a driver needs credentials

    The Add driver SIM button does more than write a row. It checks that a licence is free, registers the driver with Telenity, stores the returned id, and records that consent is pending — which is when the driver receives the text.

    This changes what your team sees. A truck is not tracked the moment a number is typed in. It is tracked when the driver replies. The chip needs to say so: awaiting driver consent, then tracking.

    There may be a shortcut worth using

    Telenity's answer was that we must enable tracking ourselves "if you import the number first and then get the consent". Their document also describes IVR consent as an advance model: a driver can call and press 1 before being registered at all.

    If a driver consents during induction rather than when a truck is assigned, importing them later should return tracking already enabled — no waiting, no chasing. That would be a much better operational flow, and it is worth confirming at PoC. It only helps for Airtel, Vi and BSNL drivers, though: Jio is SMS-only, so Jio drivers must still be imported first.

  4. Consent chasing needs credentials

    A new scheduled job sweeps drivers whose consent is still pending, checks their status, and switches tracking on the moment it turns to allowed. Without this step no position ever arrives, because Telenity does not enable tracking for us.

    It also watches expiry — consent lapses after 180 days on Jio — and re-flags a driver for a fresh consent request when it does.

  5. Polling, rebuilt around the bulk call needs credentials

    Today the poller loops one driver at a time with a pause between each. Telenity offers a single call returning up to 200 numbers, which is both faster and easier on their rate limits. Our fleet fits comfortably inside one call.

    Only successful fixes are stored. A driver whose phone is off produces a logged reason rather than a gap nobody can explain.

    Polling every 30 minutes. Telenity refresh positions every 15, so we are deliberately taking every second fix — around 34 a day per truck through the 6 am to 11 pm window. That is far denser than the toll data and light on everyone's systems. If the trail ever looks too coarse, moving to 15 minutes is a one-line change.

  6. Removing a driver needs credentials

    Turning a SIM off has to switch tracking off and then delete the entity, otherwise the licence stays consumed. Their documentation notes a licence can be held for 24 hours after tracking stops, which affects whether we should disable tracking between trips at all — also in the email.

  7. Interface and tests can start now

    Popups swap the invented accuracy figure for the real place name. The SIM chip gains its consent states. The test suite grows cases for a driver who has not yet consented, and for a phone that is switched off — the two situations your team will actually hit.

Status is doing two jobs, and the distinction matters operationally. Awaiting driver consent means the driver has to act and someone should chase them. Consented — enabling tracking means Telenity are satisfied and we have not yet switched tracking on; nobody needs chasing, the system just has not caught up. Collapsing those into one "pending" would send your team after the wrong person.

Resend needs a guard, or it will lock drivers out

Telenity's own warning on the re-initiate call: numbers get locked for 24 hours at the operator end when multiple hits are received. A "resend to all selected" button is precisely the shape that produces repeat hits — one impatient click a few minutes after the first and that driver is unreachable for a day.

So the screen records when each number was last sent, and the button greys out until enough time has passed, on the row and in bulk. The tooltip should say when it becomes available again rather than failing silently.

Resend only exists for Jio

The re-initiate endpoint is documented for Jio numbers only. Airtel, Vi and BSNL have no equivalent — for those drivers the route is the IVR line, which they call themselves. The button should therefore be disabled for non-Jio numbers with that explanation, rather than offering an action that cannot work.

Same caveat on Valid till: the 180-day expiry is documented for Jio, and we do not yet know whether other operators expire at all. Expect that column to be blank for non-Jio drivers until Telenity confirm otherwise.

Deleting removes the driver at Telenity and frees the licence, though not instantly — a licence can be held for 24 hours after tracking stops. On our side the record is kept rather than erased, so a truck's history survives a change of driver.

The pilot

Five drivers · learning the operation, not just the code

The first phase is deliberately small: five drivers out of a fifty-licence allocation, run until the whole operation is understood — onboarding a tranco, briefing drivers, collecting consent, and seeing how the data actually behaves against the toll crossings we already trust. Scaling up is a commercial decision to take afterwards, not a technical one.

That scope changes what is worth building first. At five trucks the backend is the easy part. What decides whether the pilot succeeds is whether the operations team can see, at a glance, which drivers have consented and which are sitting idle — and, when a truck shows nothing, why. Consent visibility earns its place ahead of any polling sophistication.

The number worth measuring

Consent conversion — how many of the five drivers actually reply to the SMS. If it is four in five, this scales. If it is one in five, no amount of code fixes it and the answer lies in the IVR route, or briefing drivers at induction, or something else entirely. That figure will be clear within a week and is worth more than anything in the rest of this plan.

Answered so far

No source-IP allow-listing. Our hosting needs no change. That was the risk most likely to force work outside the application itself, and it is closed.

Enabling tracking is always manual. Confirmed: after consent arrives we must call Modify ourselves. The consent-chasing job in phase 4 is therefore required, not optional.

Credentials come with the PoC. The collection, auth key and consent credentials are all issued when the PoC or demo service is initiated. So the remaining blocker is a commercial step rather than a technical question — there is nothing further to ask.

Customer-id. Telenity say it is returned in the Auth response, though the sample in their document does not show it. We will read it if present and fall back to the Modify response, which does carry customerId. No need to chase this.

Positions refresh every 15 minutes on our account, and we hold 50 licences. Both are comfortable for a pilot.

Accuracy is quoted as 5 metres, but that needs checking. SmartTrail is a network-based service — Telenity describe it as using "network provided location information", which is cell positioning rather than handset GPS, and is normally hundreds of metres. Their own sample returns an address of district granularity. The answer decides whether we may draw the truck snapped to a road or must keep the looser dotted treatment, so it is worth one minute of the PoC call: fetch a position for someone standing next to you and compare.

Risks worth naming now

In rough order of how much trouble they cause

  • The same API keys work on staging and production. Telenity confirmed this, which means there is no credential boundary protecting live data from a test run. Our own configuration has to keep the two apart carefully.
  • Consent adoption. Tracking depends on drivers replying to a text message. If they ignore it, the truck simply never appears. This is an operational problem more than a technical one, and it needs a person chasing it — worth deciding who owns that.
  • Licence quota. Every registered driver consumes one. If the quota is smaller than the fleet, we need a policy for which trucks get tracked.
  • Refresh rate may disappoint. Their tracking frequency, not our polling, sets how often a position actually changes. If it is slower than hourly, the trail will be coarser than the mock has led us to expect.
  • Jio has its own rules — SMS-only consent, 180-day expiry, and a 24-hour lockout if the re-initiate call is repeated. Worth knowing how much of the fleet is on Jio.

Going live

Three stages, each reversible

First, a single test number — someone on the team who can consent on demand and confirm where they actually are. This proves the whole chain end to end and costs one licence.

Then one real truck with a willing driver, watched for a couple of days against its FASTag crossings. That comparison is the honest test of whether the SIM trail is trustworthy, because for once we have a second source to check it against.

Then the rest of the fleet, at whatever pace consent collection allows. Mock mode stays available throughout, so a demo is never dependent on live credentials.

What we can build before the credentials arrive

Nothing here needs Telenity

Two pieces are genuinely unblocked, and between them they cover what the pilot leans on most heavily.

The driver SIM screen

The recommended first piece, specified above. The table, the pending-only toggle, the selection and the bulk bar can all be built now against our own database, along with the columns that hold consent state and the Telenity entity id. Only the buttons' underlying calls wait on credentials — so the screen can be finished and reviewed before the PoC, then wired up in an afternoon.

Removing the invented accuracy

The accuracy_m field I added does not exist in the real API. It runs through the schema, three map popups and a test. Taking it out now, and leaving room for the address text Telenity return instead, avoids carrying a fiction into the pilot.

Plain failure reasons

Mapping Telenity's result codes to readable text — phone switched off, out of coverage, not provisioned — so that when a truck shows nothing during the pilot, the reason is on screen rather than in a log nobody reads.

Everything else — the client itself, onboarding, consent chasing, polling, removal — waits on the PoC credentials, and should follow quickly once they land.
